# Spice of Life: Fabric Flavor 1.20.1 降级与 MySQL 多服同步分析

## 1. 文档目标

本文评估以下两项需求的实现难度、风险和推荐方案：

1. 将当前 `3.3.0 / Minecraft 1.21.1 / Java 21` 版本降级兼容到 `Minecraft 1.20.1 / Fabric / Java 17`。
2. 增加 MySQL 玩家数据同步，使多个 Fabric 子服共享本模组的玩家进度，并满足：
   - 玩家登录服务器时异步加载和同步数据；
   - 所有 JDBC/MySQL 操作都不在 Minecraft 服务端线程执行；
   - 数据库异常不能卡住服务器 tick；
   - 快速跨服、重复写入和清空数据时尽量避免旧数据覆盖新数据。

本文只进行分析和设计，不代表功能已经实现或通过运行态验收。

## 2. 结论摘要

### 2.1 总体结论

该需求技术上可实现。确认允许跨服后在 5 秒内完成同步后，综合难度调整为 **中等偏高，约 6.5/10**。

版本降级本身不是最高风险，因为仓库历史中已经存在可复用的 1.20.1 实现：

- 提交 `8983056` 仍是 `Minecraft 1.20.1`、`Fabric API 0.92.6+1.20.1`、`Java 17`，模组版本为 `2.7.0`。
- 提交 `56dc72c` 才将项目升级到 `Minecraft 1.21.1`。
- 当前 `3.3.0` 比历史 `2.7.0` 多了重构后的模块、饥饿功能、白名单、网络包调整和若干修复，不能直接回退到旧提交发布。

推荐从当前 `3.3.0` 创建独立的 `1.20.1` 分支，保留现有业务逻辑，再参考 `8983056` 的旧 API 写法替换不兼容部分。这样不会丢失 2.7.0 之后的功能。

MySQL 同步的真正难点不是 JDBC 连接，而是以下一致性问题：

- 登录异步加载完成前，玩家可能已经食用新食物；
- 玩家刚在 A 服食用食物就立即切换到 B 服，B 服查询可能早于 A 服提交；
- `/sol2f clearhealthy` 或死亡重置属于删除操作，不能简单使用集合并集，否则被删除的数据会再次出现；
- 数据库线程不能直接读取或修改 `ServerPlayerEntity`、玩家 NBT、属性和网络连接；
- 玩家可能在查询完成前离线或再次登录，需要防止过期回调写到新会话。

因此需要一个很小但明确的玩家会话同步层，不能只在 JOIN 事件里套一个 `CompletableFuture` 后直接改玩家对象。

### 2.2 已确认的一致性要求

- 不要求玩家切服瞬间严格一致；
- 在数据库正常的情况下，玩家进入目标子服后 **5 秒内同步完成即可**；
- 玩家登录不能等待数据库，更不能阻塞 Minecraft 服务端线程；
- 第一版使用 MySQL 即可，不需要为了零延迟引入 Redis 或代理切服锁；
- 推荐在登录时立即异步查询一次，并在登录约 5 秒时执行一次补偿复查；
- 补偿复查只执行一次，不做固定周期轮询，避免在线玩家持续产生数据库查询。

### 2.3 预计工期

以下为生产可用版本的估算，不包括等待外部测试服务器、数据库账号或原作者授权的时间：

| 阶段 | 预计工作量 |
| --- | ---: |
| 修复构建入口、建立 1.20.1 分支 | 0.5 天 |
| 1.20.1 API 降级与客户端/服务端编译修复 | 1.5～2.5 天 |
| MySQL 表结构、连接池、异步会话和迁移实现 | 2～3 天 |
| 清空/死亡重置、断线重连、关闭刷写处理 | 1～2 天 |
| 双子服、真实客户端、数据库故障回归 | 1.5～2.5 天 |
| 合计 | **约 6～10 个工作日** |

如果只实现“登录 SELECT、食用 INSERT”的理想路径，可以压缩到 3～5 天，但无法称为可靠的多子服同步版本。

## 3. 当前项目结构与数据链

### 3.1 当前技术基线

- Minecraft：`1.21.1`
- Java：`21`
- Fabric Loader：`0.18.4`
- Fabric API：`0.116.8+1.21.1`
- Loom：`1.10.1`
- 配置：Cloth Config + AutoConfig
- 网络：新版 `CustomPayload`、`PacketCodec`、`PayloadTypeRegistry`
- 玩家进度：玩家实体 NBT 中的 `sol2f.consumed_foods`
- 生命值：根据已食用食物集合实时计算，不需要单独存储到数据库

项目共有 26 个 Java 文件，主要分层如下：

| 模块 | 作用 |
| --- | --- |
| `SpiceOfLifeFabricFlavor` | 公共初始化、配置、物品、网络包和事件注册 |
| `SpiceOfLifeFabricFlavorClient` | 客户端缓存、网络接收、Tooltip 和快捷键 |
| `HealthModule` | 食物记录、生命值增益和玩家 NBT 读写 |
| `HungerModule` | 自然饥饿和睡眠饥饿 |
| `ServerEvents` | 登录、重生、维度复制、睡眠和 tick 事件 |
| `PlayerEntityMixin` | 向实体注入持久化 NBT 和计数器 |
| `ItemStackFinishMixin` | 捕获玩家完成食用物品的事件 |
| `network/payload` | 1.21.1 新版客户端与服务端数据包 |

### 3.2 当前玩家数据

当前真正需要跨服共享的数据是：

- `consumed_foods`：玩家已经食用过的物品注册 ID 集合；
- `data_version`：本地 NBT 数据版本。

以下数据不建议跨服同步：

- `HungerTickCounter`：当前子服的饥饿计时进度；
- `SleepStartTick`：一次睡眠过程中的临时状态；
- 当前生命值和最大生命值：应由当前服务器根据共享食物集合和本服配置重新计算；
- 客户端 GUI 缓存：登录后重新下发即可。

本文后续所说的“玩家数据同步”，默认指本模组的已食用食物进度，而不是同步整个 Minecraft 玩家 NBT、背包或位置。

### 3.3 当前登录流程

当前玩家 JOIN 后立即：

1. 从玩家本地 NBT 读取 `consumed_foods`；
2. 计算并应用最大生命值修饰符；
3. 向客户端发送已食用食物列表；
4. 向客户端发送本服全部有效食物和理论最大增益。

接入 MySQL 后，步骤 1 变为异步流程，步骤 2～4 必须等数据库结果回到服务端线程后再执行，否则客户端会先收到旧 NBT 数据，随后又被数据库结果覆盖。

## 4. 当前已发现的前置问题

### P0：Gradle Wrapper 指向作者内网地址

当前 `gradle/wrapper/gradle-wrapper.properties` 使用：

```text
http://192.168.3.30:5244/d/file/mirror/gradle/gradle-8.14.2-bin.zip
```

实际执行 `gradlew.bat build --no-daemon` 时连接超时，因此当前仓库在外部环境不能直接完成基线构建。

降级前必须将 Wrapper 改回可公开访问并可校验的 Gradle 官方分发地址，然后先证明当前分支可以构建。否则后续编译错误会与 Wrapper 故障混在一起。

### P0：仓库许可证限制

仓库 `LICENSE` 为 `All Rights Reserved`，明确禁止未经著作权人书面许可重新分发和修改。

技术开发前应确认已经得到原作者授权。本文只评估技术方案，不代表许可证问题已经解决。

### P1：没有自动化测试

当前没有 `src/test`、GameTest 或网络协议测试。1.20.1 降级和数据库同步都涉及大量边界情况，至少需要增加纯 Java 单元测试和数据库集成测试。

### P1：Mixin 目标过宽

名为 `PlayerEntityMixin` 的类实际注入到 `Entity.class`，因此所有实体都会增加本模组字段。对大量实体的模组服务器而言，这会产生没有必要的对象内存开销。

在本次重构中应评估将持久化范围缩小到玩家，或让 MySQL 会话缓存成为在线期间的主要状态，只保留玩家 NBT 作为本地回退和旧数据迁移来源。

### P1：加载数据和“新增食物奖励”没有分离

`applyHealthModifier` 同时负责应用属性和“增加时恢复生命”。登录、重生或数据库加载完成后调用它，也可能触发恢复生命逻辑。

建议拆成两个简单方法：

- 应用当前进度对应的属性，不治疗玩家；
- 只有确认新增食物时才执行配置中的恢复生命效果。

这不是为了抽象，而是为了消除登录同步产生的错误副作用。

### P2：正常保存会输出大量 INFO 日志

每次保存食物集合都会输出保存前后完整列表。模组包食物较多时会制造大量日志和字符串对象。正常成功日志应降为开发模式或 DEBUG，失败日志保留 WARN/ERROR。

## 5. 1.21.1 降级到 1.20.1 的改造点

### 5.1 推荐分支策略

推荐：

1. 从当前 `1.21` 分支的 `3.3.0` 创建 `1.20.1` 分支；
2. 保留当前模块划分和业务功能；
3. 参考历史提交 `8983056` 替换 Minecraft/Fabric API；
4. 不引入 Architectury、多版本反射层或复杂工厂；
5. 两个 Minecraft 大版本通过 Git 分支维护。

不推荐直接从 `8983056` 继续开发，因为这会丢失 2.7.0 之后的白名单、饥饿系统、重构和修复，再手工补回的风险更高。

### 5.2 主要 API 差异

| 范围 | 当前 1.21.1 | 1.20.1 需要改为 | 难度 |
| --- | --- | --- | --- |
| Java | Java 21 | Java 17 | 低 |
| 食物判断 | `DataComponentTypes.FOOD` | `ItemStack`/`Item#getFoodComponent()` 旧接口 | 中 |
| 网络协议 | `CustomPayload`、`PacketCodec` | `Identifier + PacketByteBuf` | 中高 |
| 网络注册 | `PayloadTypeRegistry` | 旧版全局 Receiver 回调 | 中 |
| Identifier | `Identifier.of(...)` | `new Identifier(...)` | 低 |
| 属性修饰符 | Identifier 作为修饰符 ID | UUID、名称、`Operation.ADDITION` | 中 |
| GUI 背景 | 四参数背景渲染 | 1.20.1 单参数 `renderBackground` | 低 |
| 鼠标滚轮 | 四参数 `mouseScrolled` | 三参数旧签名 | 低 |
| Tooltip | 新版回调和数据组件 | 1.20.1 Tooltip 回调和食物属性 | 中 |
| Mod Menu | 11.x | 7.2.x | 低 |
| Cloth Config | 15.x | 11.1.x | 低 |
| Fabric API | 0.116.x | 0.92.6 | 中 |

### 5.3 网络协议建议

1.20.1 应恢复为固定 `Identifier` 通道和 `PacketByteBuf` 编解码，但保留当前数据含义：

- `s2c_food_list`
- `s2c_all_food_list`
- `s2c_health`
- `s2c_health_max`
- `c2s_request_food_list`
- `c2s_request_all_food_list`
- `open_food_book_screen`

需要为列表长度和单个字符串长度增加上限，避免异常或恶意数据包导致过量内存分配。服务端只接受无载荷的请求包，不接受客户端提交玩家进度。

### 5.4 食物识别建议

1.20.1 没有 1.21.1 的数据组件系统。基础兼容可以使用历史版本已验证的 `getFoodComponent()` 逻辑。

但当前版本曾专门修改食用注入点以兼容动态食物属性，因此实现时还需要用实际 1.20.1 模组包验证：

- 原版食物；
- 常规 Mod 食物；
- 通过 NBT、Mixin 或 AppleSkin 兼容层动态提供饥饿值的食物；
- 饮料、药水和非食物 `finishUsing` 物品不能被错误记录。

如果 `ItemStack.finishUsing` 在 1.20.1 映射中可稳定注入，应优先保留当前注入位置；食物判定再改用 1.20.1 可用接口。不能仅因为旧代码注入 `Item.finishUsing` 就无条件退回旧位置。

### 5.5 版本降级风险判断

版本降级的代码量中等，但已有历史 1.20.1 版本作为直接参考，因此风险可控。预计主要时间花在客户端 GUI、网络协议和实际 Mod 食物兼容验证，而不是核心生命值公式。

## 6. MySQL 多子服同步的推荐模型

### 6.1 基本原则

1. UUID 是玩家唯一身份，玩家名只作为辅助审计字段。
2. 玩家在线时只从内存会话读取进度，不能在食用事件、GUI 请求或 tick 中查询 MySQL。
3. JDBC 查询、建表、写入、重试全部在专用有界线程池中执行。
4. 数据库线程只处理普通 DTO、UUID 和字符串集合，绝不访问 Minecraft 实体和世界对象。
5. 数据库结果必须通过 `MinecraftServer.execute(...)` 回到服务端线程后，才能更新玩家 NBT、属性和网络包。
6. 新食物使用幂等写入，重复提交不能制造重复数据。
7. 清空数据使用“代次 generation”，防止旧异步写入把已经删除的数据复活。
8. 本地 NBT 保留为旧版数据迁移和数据库故障回退，不再被视为所有子服的全局权威数据。

### 6.2 为什么不建议整份 JSON 覆盖

将整个食物集合存成一个 JSON/TEXT 字段虽然代码少，但两个子服同时保存时会产生典型的最后写入者覆盖问题：

- A 服集合为 `{apple, bread}`；
- B 服集合为 `{apple, carrot}`；
- 两边异步 UPDATE 后，最终可能只剩其中一份，而不是三种食物的并集。

推荐每个食物一行，新增食物使用主键去重和 `INSERT IGNORE`。这种模型天然适合“食物进度大多数时候只增加”的业务。

### 6.3 推荐表结构

```sql
CREATE TABLE sol2f_player_state (
    sync_group VARCHAR(64) CHARACTER SET ascii NOT NULL,
    player_uuid CHAR(36) CHARACTER SET ascii NOT NULL,
    generation BIGINT UNSIGNED NOT NULL DEFAULT 0,
    last_player_name VARCHAR(64) NOT NULL DEFAULT '',
    updated_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
        ON UPDATE CURRENT_TIMESTAMP(3),
    PRIMARY KEY (sync_group, player_uuid)
) ENGINE=InnoDB;

CREATE TABLE sol2f_consumed_food (
    sync_group VARCHAR(64) CHARACTER SET ascii NOT NULL,
    player_uuid CHAR(36) CHARACTER SET ascii NOT NULL,
    generation BIGINT UNSIGNED NOT NULL,
    food_id VARCHAR(191) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    source_server VARCHAR(64) CHARACTER SET ascii NOT NULL DEFAULT '',
    first_eaten_at TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (sync_group, player_uuid, generation, food_id)
) ENGINE=InnoDB;
```

说明：

- `sync_group` 用于隔离不同服务器网络，避免共用一个数据库时串数据；
- `source_server` 只用于排查来源，不参与玩家身份判断；
- `generation` 用于实现安全清空；
- 使用固定表名，不提供可直接拼接到 SQL 的任意表名配置，减少 SQL 注入和配置错误；
- 当前规模下使用可读的 `CHAR(36)` UUID 足够，没必要为了少量空间引入 `BINARY(16)` 转换复杂度。

### 6.4 清空数据为什么需要 generation

假设玩家在 A 服执行清空时，B 服还有一个较早提交的食物写入任务正在队列中。如果只是 DELETE，旧任务可能在 DELETE 之后重新 INSERT，使食物再次出现。

推荐清空时在事务中递增 `sol2f_player_state.generation`。之后登录只读取当前 generation 的食物。旧任务即使晚到，也只会写入旧 generation，不会再被读取。

旧 generation 的行可以在低峰期异步清理，不需要在玩家命令路径同步删除。

## 7. 异步线程与玩家会话设计

### 7.1 最小类结构

建议只增加必要类，不引入 Repository 接口、工厂套工厂或依赖注入框架：

| 类 | 职责 |
| --- | --- |
| `DatabaseConfig` | 读取和校验数据库配置 |
| `MySqlStorage` | 建表、加载、插入、递增 generation 和关闭连接池 |
| `PlayerDataSyncService` | 管理在线玩家会话、异步任务、合并和主线程回调 |
| `PlayerFoodSnapshot` | 不可变数据库结果 DTO，可使用 Java 17 record |

连接池建议使用 HikariCP。HikariCP 只负责连接池，不会自动把 JDBC 查询变成异步，因此仍然需要专用、有界的数据库执行器。

实现时所有方法都应添加最基本的中文注释，并避免非空断言或假定回调时玩家仍在线。

### 7.2 玩家会话状态

每个在线玩家维护一个很小的会话：

- `sessionToken`：本次登录唯一令牌；
- `state`：`LOADING`、`READY` 或 `FALLBACK`；
- `generation`：数据库当前代次；
- `foods`：当前服务端线程使用的食物集合；
- `pendingFoods`：数据库加载期间新食用的食物；
- `dirty`：本地存在尚未确认写入数据库的变化。

会话对象不需要复杂锁。推荐让业务状态只在服务端线程修改，数据库线程只返回不可变结果。跨线程共享只通过 Future 结果和会话令牌完成。

### 7.3 登录流程

1. JOIN 事件在服务端线程创建新会话并标记为 `LOADING`。
2. 在服务端线程读取一次本地 NBT 快照，然后不再让数据库线程接触玩家对象。
3. 数据库执行器按 `sync_group + UUID` 异步读取玩家状态和当前 generation 食物。
4. 查询期间玩家食用新食物时，将 ID 放入 `pendingFoods`，不能丢弃，也不能用未加载完成的集合覆盖数据库。
5. 查询完成后调用 `server.execute(...)`。
6. 主线程检查玩家仍在线且 `sessionToken` 一致；不一致则丢弃这个过期结果。
7. 合并数据库数据和本次会话的 pending 数据，写回内存和玩家 NBT。
8. 应用生命值属性并向客户端发送完整同步包。
9. 将 pending 新增项异步批量写入 MySQL。
10. 玩家登录约 5 秒时进行一次异步补偿查询；若发现其他子服刚提交的新食物，则回到服务端线程增量合并并刷新属性和客户端缓存。

数据库首次没有该玩家记录时，可以将旧 NBT 食物列表作为一次性迁移基线写入 generation 0。

数据库已有记录时，不能无条件把本地 NBT 与数据库取并集，否则其他子服已经执行过清空的数据会被旧 NBT 复活。NBT 中需要同时保存最近确认的 generation 和 dirty 状态，只有 generation 一致或明确处于故障回退状态时才允许合并。

### 7.4 食用新食物流程

1. 食用事件仍在服务端线程判断黑名单、白名单和是否首次食用。
2. 先更新内存会话和本地 NBT，让玩家体验不依赖数据库延迟。
3. 应用生命值、治疗效果和客户端数据包。
4. 向数据库执行器提交幂等 `INSERT IGNORE`。
5. 写入成功后，在服务端线程将对应 dirty 状态标记为已确认。
6. 写入失败时保留 dirty 数据并按有界退避策略重试，不能无限高速重试或静默丢弃。

每次真正首次食用只需要一次很小的 INSERT，不需要保存整份食物集合。

### 7.5 玩家离线和服务器关闭

- 玩家离线后移除在线会话，但已经提交的 JDBC Future 可以继续完成；
- 回调不得再访问已离线的 `ServerPlayerEntity`；
- 数据库写入使用 UUID 和不可变参数，因此玩家离线不会影响写入；
- 服务器关闭时停止接收新任务，并对已经提交的异步写入进行有限时间等待；
- 等待只是等待异步任务结束，不能在服务端线程直接执行 JDBC；
- 超时后记录仍未完成的任务数量，不能把超时写成“已全部保存”。

## 8. 数据库配置建议

建议保留现有玩法配置文件不变，新增独立数据库配置，例如：

```json
{
  "enabled": true,
  "jdbcUrl": "jdbc:mysql://127.0.0.1:3306/minecraft?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai",
  "username": "sol2f",
  "password": "change-me",
  "syncGroup": "main-network",
  "serverId": "survival-1",
  "maximumPoolSize": 4,
  "minimumIdle": 1,
  "connectionTimeoutMs": 3000,
  "queryTimeoutSeconds": 5,
  "loginReconcileDelaySeconds": 5,
  "executorThreads": 2,
  "executorQueueSize": 1024
}
```

配置要求：

- `syncGroup`：需要共享数据的子服保持一致；
- `serverId`：每个子服唯一，只用于日志和来源审计；
- `loginReconcileDelaySeconds`：登录后的补偿复查延迟，当前确认值为 5 秒；
- 数据库密码绝不能输出到日志；
- 线程数和连接池不宜按玩家数增长；
- 建议默认连接池最大值 4，数据库执行线程 2，再根据实际登录峰值调整；
- 队列必须有上限，队列满时保留本地 dirty 数据并告警，不能无限占用内存。

实际配置文件路径和是否沿用 AutoConfig，可在实现前确认。无论采用 JSON 还是其他格式，都应与玩法配置分离。

## 9. 一致性边界

### 9.1 MySQL-only 的实际一致性

使用“事件发生后异步写 MySQL、下一个子服登录时异步读 MySQL”属于最终一致性。当前已经确认允许在玩家进入目标子服后 5 秒内完成同步，因此 MySQL-only 方案可以满足需求。

正常情况下延迟很短，但存在以下窗口：

1. 玩家在 A 服刚吃下食物；
2. A 服异步 INSERT 已排队但尚未提交；
3. 玩家立即切换 B 服；
4. B 服 SELECT 先执行，暂时看不到刚才的食物。

在只允许 MySQL、且禁止阻塞跨服流程的条件下，无法数学上保证这个窗口为零。

本项目采用以下缓解方案：

- 食物 INSERT 使用高优先级、小事务并立即提交；
- 玩家登录时立即进行第一次异步查询；
- 玩家登录约 5 秒时执行一次异步补偿查询，合并这段时间内其他子服完成的写入；
- 两次查询都通过 session token 防止过期结果污染新的登录会话；
- 不要求代理切服前等待，也不引入 Redis。

第一版的明确承诺调整为：**数据库正常时，跨服数据在目标子服登录后的 5 秒内收敛；不承诺切服瞬间零延迟一致。**

### 9.2 子服配置和模组列表差异

如果多个子服使用不同食物模组、黑名单、白名单或生命值公式，必须提前决定健康增益的语义。

推荐：

- MySQL 保存全局已食用 ID；
- 当前服务器计算生命值时，只统计本服存在且通过本服黑白名单的食物；
- 已卸载或本服不存在的物品 ID 保留在数据库，但不在本服贡献生命值；
- 若希望所有子服显示完全一致的生命值，则所有参与同一 `syncGroup` 的子服必须使用相同模组列表和健康配置。

当前代码在登录时可能直接按全部 NBT ID 数量计算生命值。多子服版本必须修正这一点，否则玩家可从其他子服的独有食物获得本服不应存在的增益。

### 9.3 UUID 和代理配置

数据库必须使用 UUID，而不是玩家名。

如果后端 Fabric 子服运行在离线模式并通过 Velocity/Bungee 类代理连接，必须保证所有子服收到一致、可信的转发 UUID。代理转发配置错误会让同一玩家在不同子服生成不同 UUID，从而出现多份数据库记录。

## 10. 故障策略

### 10.1 数据库启动失败

推荐默认采用“本地回退但明确告警”：

- 服务器继续启动；
- 玩家暂时使用本地 NBT；
- 会话标记为 `FALLBACK`；
- 后台有界重连；
- 数据库恢复后只按 generation 和 dirty 标记安全合并；
- 日志和状态命令明确显示当前不是多服同步状态。

也可以提供严格模式，在数据库不可用时拒绝玩家进入，但不建议作为默认行为。

### 10.2 登录查询超时

- 不能卡住服务端线程；
- 超时后进入本地回退；
- 迟到的旧查询结果必须通过 session token 拦截；
- 不应在登录期间无限重试。

### 10.3 清空或死亡重置失败

清空属于破坏性操作，数据库失败时不应假装成功。

推荐：

- `/sol2f clearhealthy` 先提示“正在处理”，generation 更新成功后再在主线程清空并提示成功；
- 更新失败则保留原数据并提示失败；
- `resetOnDeath` 默认关闭，开启后需要专门测试数据库失败语义；
- 第一版可选择数据库不可用时跳过跨服重置并告警，避免各子服产生互相覆盖的状态。

## 11. 性能与内存控制

### 11.1 必须遵守的性能边界

- 不在 tick、Tooltip、GUI 请求或生命值计算路径访问数据库；
- 登录只进行一次小型状态查询和一次食物集合查询；
- 新食物只提交一条幂等 INSERT；
- 旧 NBT 首次迁移使用批量 INSERT；
- PreparedStatement 复用由连接池和驱动处理，不手工维护危险的跨连接 Statement 缓存；
- 玩家在线集合使用 HashSet，返回客户端前再创建快照；
- 数据库任务队列有界；
- 重试使用指数退避并设置最大间隔；
- 成功保存不输出完整食物列表 INFO 日志；
- 查询结果和数据包设置合理数量上限。

### 11.2 连接池建议

这类业务数据库流量很低，不需要大连接池。每个子服默认：

- 最小空闲连接：1；
- 最大连接：4；
- JDBC 执行线程：2；
- 有界任务队列：约 1024；
- 连接和查询超时：3～5 秒范围。

最终数值应结合子服数量、登录峰值和 MySQL 最大连接数实测，而不是简单按在线玩家数放大。

- 新玩家首次登录自动创建状态；
- 旧 NBT 玩家首次登录可以迁移；
- A 服食用后立即进入 B 服，B 服应在登录后 5 秒内加载相同进度；

- 主线程日志中没有 JDBC 调用；
- 模拟慢查询时 MSPT 不因数据库等待明显升高；

## 14. 开发前需要确认的业务决定

以下问题不会阻止技术评估，但在正式编码前需要确认：

1. 多个子服的食物模组列表和健康配置是否完全相同？
2. 本次同步是否只包含已食用食物，还是还要同步饥饿计时等状态？本文推荐只同步食物进度。
3. 数据库不可用时，是允许玩家使用本地 NBT 进入，还是拒绝登录？本文推荐本地回退并明确告警。
4. 是否启用 `resetOnDeath`？如果启用，需要确认数据库失败时的死亡重置策略。
5. MySQL 版本是 5.7、8.0 还是 MariaDB？实现时需要用实际版本做集成测试。
6. 是否已经取得原作者对修改和重新分发的书面授权？

## 15. 最终建议

推荐按以下最小而可靠的路线实施：

1. 先修复 Wrapper，证明现有项目能构建；
2. 从当前 3.3.0 建立独立 1.20.1 分支，不直接回退到旧版发布；
3. 使用历史 2.7.0 代码作为 API 迁移参考；
4. 先完成无数据库的 1.20.1 功能回归；
5. 再加入 HikariCP、有界数据库执行器和玩家 READY 会话；
6. 食物按行幂等存储，清空使用 generation；
7. 数据库线程永远不碰 Minecraft 对象；
8. 最后使用两个真实 Fabric 子服、真实 MySQL 和真实客户端完成跨服验收。

按这条路线开发，不需要引入大型框架，也能把异步数据库、多服冲突和版本兼容的主要风险控制住。
